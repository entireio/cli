Briefing: Per-agent live streaming for entire review

  Background

  PR #1184 (just merged-or-pending) fixed the drill-in viewport for entire review multi-agent runs. One issue
  explicitly deferred from that PR: each agent buffers its stdout until completion, so the drill-in event buffer
  fills in one burst at end-of-run instead of streaming as the agent works. We labeled this "PR B" in the
  brainstorm.

  Current behavior (the problem)

  - RunMulti (cmd/entire/cli/review/run_multi.go) fans events from per-agent goroutines into a single dispatch loop
  - The TUI sink (tui_sink.go) is ready to display events as they arrive — AgentEvent is called per event, dispatch
  is already serialized
  - The bottleneck is upstream: each agent's reviewer/parser doesn't emit AssistantText / ToolCall events until the
  agent process exits, because each adapter waits for the full stdout before parsing
  - User-visible symptom: drill-in shows "(0 events)" until the agent finishes, then jumps to "(N events)" all at
  once

  Target behavior

  Each agent emits events incrementally as stdout arrives. Drill-in shows live progress; dashboard preview column
  updates in real time.

  Key files

  - Shared scaffolding: cmd/entire/cli/review/types/template.go — ReviewerTemplate (Spawn → pipe stdout → run parser
   → forward events → close). Each agent supplies BuildCmd and Parser.
  - Per-agent reviewers (each has its own parser):
    - cmd/entire/cli/agent/claudecode/reviewer.go — Claude Code uses stream-json output, should be line-by-line
  already; verify why events arrive batched
    - cmd/entire/cli/agent/codex/reviewer.go — Codex includes filterCodexOutput chrome filter; check if filter
  buffers before emit
    - cmd/entire/cli/agent/geminicli/reviewer.go — Gemini CLI parser
  - Event types: cmd/entire/cli/review/types/event.go — AssistantText, ToolCall, RunError, RunFinished
  - Sinks: cmd/entire/cli/review/tui_sink.go, dump.go, synthesis_sink.go — all already handle per-event dispatch

  Investigation starting points

  1. Add a debug log in Run's event forwarding loop (or in ReviewerTemplate's pipe goroutine) printing time.Now() +
  event kind. Run a real review and check whether events arrive at staggered timestamps or all at once.
  2. If they're staggered at the template level but show up batched in the TUI → the issue is in TUI rendering or
  sink dispatch.
  3. If they're batched at the template level → check each parser: are they using bufio.Scanner (line-by-line, OK)
  or reading full stdout (batched, BAD)?
  4. Specifically suspect Codex — filterCodexOutput may collect chrome-filtered output before forwarding.

  Constraints (do NOT break)

  - Serial-dispatch contract: RunMulti already serializes events through a single dispatch loop. Don't move to
  per-sink goroutines.
  - RunFinished blocks on TUI dismissal: don't change the order of RunFinished vs sink writes.
  - Cancellation: events arriving after ctx.Done() should still flush (we want partial output preserved on Ctrl+C).
  - tea.Program.Send thread safety: the TUI's Send is goroutine-safe per Bubble Tea, but the sink relies on dispatch
   serialization — keep that.

  Smoke test

  After implementing, run entire review with at least two agents configured (claude-code + codex). In the drill-in
  (Ctrl+O during the run), the event buffer should grow visibly while the agent is still working. Compare against
  the current behavior (drill-in is empty until end).

  Anti-features (don't add)

  - Don't add a throttle / debounce layer — let events flow as they arrive
  - Don't add per-agent buffering "to avoid TUI thrash" — the viewport handles that
  - Don't change the AgentReviewer interface — extend parsers in place

  Useful context from prior work

  - Bubble Tea v2 mouse mode: v.MouseMode = tea.MouseModeCellMotion (per-View field), NOT tea.WithMouseCellMotion()
  (v1 program option)
  - viewport.AtBottom() + conditional GotoBottom() is the auto-follow pattern in refreshDetailContent
  - cmd/entire/cli/review/tui_text.go has wrapDisplayWidth and truncateDisplayWidth helpers — paragraph-preserving
  wrap, ANSI-aware

## Instruction Priority

Superpowers skills override default system prompt behavior, but **user instructions always take precedence**:

1. **User's explicit instructions** (CLAUDE.md, GEMINI.md, AGENTS.md, direct requests) — highest priority
2. **Superpowers skills** — override default system behavior where they conflict
3. **Default system prompt** — lowest priority

If CLAUDE.md, GEMINI.md, or AGENTS.md says "don't use TDD" and a skill says "always use TDD," follow the user's instructions. The user is in control.

**In Claude Code:** Use the `Skill` tool. When you invoke a skill, its content is loaded and presented to you—follow it directly. Never use the Read tool on skill files.

**In Gemini CLI:** Skills activate via the `activate_skill` tool. Gemini loads skill metadata at session start and activates the full content on demand.

**In other environments:** Check your platform's documentation for how skills are loaded.

## Red Flags

These thoughts mean STOP—you're rationalizing:

| Thought | Reality |
|---------|---------|
| "This is just a simple question" | Questions are tasks. Check for skills. |
| "I need more context first" | Skill check comes BEFORE clarifying questions. |
| "Let me explore the codebase first" | Skills tell you HOW to explore. Check first. |
| "I can check git/files quickly" | Files lack conversation context. Check for skills. |
| "Let me gather information first" | Skills tell you HOW to gather information. |
| "This doesn't need a formal skill" | If a skill exists, use it. |
| "I remember this skill" | Skills evolve. Read current version. |
| "This doesn't count as a task" | Action = task. Check for skills. |
| "The skill is overkill" | Simple things become complex. Use it. |
| "I'll just do this one thing first" | Check BEFORE doing anything. |
| "This feels productive" | Undisciplined action wastes time. Skills prevent this. |
| "I know what that means" | Knowing the concept ≠ using the skill. Invoke it. |

When multiple skills could apply, use this order:

1. **Process skills first** (brainstorming, debugging) - these determine HOW to approach the task
2. **Implementation skills second** (frontend-design, mcp-builder) - these guide execution

"Let's build X" → brainstorming first, then implementation skills.
"Fix this bug" → debugging first, then domain-specific skills.

**Rigid** (TDD, debugging): Follow exactly. Don't adapt away discipline.

**Flexible** (patterns): Adapt principles to context.

The skill itself tells you which.
