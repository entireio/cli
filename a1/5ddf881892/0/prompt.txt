**1. Hot-path verification.** Net win confirmed. Old: 1 unfiltered fetch covering all N archives (full blobs for entiredb's ~167 archives). New common case: 1 blobless fetch of the same N refs + ancestry walk + 1 blob top-up for only the matched archive. Since the matched archive is typically the most recent one (ancestry walk hits early), and matched-archive blob volume is ~1/N of the old payload, this is ~Nx less network traffic. Worst case: matched archive is the *oldest* — ancestry walk does N reads, then we still top up only one archive. Still strictly less data on the wire than the old path. **Fine.**

**2. Fallback retry cost.** No per-target capability caching exists (verified via grep for `allowFilter`, `filterSupport`, etc.). On a server that never supports filtered fetches, every rotation recovery pays "1 failed blobless probe + 1 full fetch." But the probe failure is fast (server refuses at advertisement time, no pack streamed), and rotation recovery is rare (only when remote rotates between user's pulls). **Acceptable as-is.** A simple in-process cache keyed by `fetchTarget` (set after first probe failure within the process) would be cheap insurance for environments with pre-push hooks running back-to-back, but probably not worth it for a recovery-only path.

**3. `missingBlobHashesInTree` performance.** The walk is unavoidable — `FlattenTree` in `handleRotationConflict` (push_v2.go:779) does the *same* recursive `repo.TreeObject` walk on this exact tree right after. Subtree reads hit go-git's storer (packfile-cached when loaded); not free, but bounded by tree size and amortized against the FlattenTree pass that immediately follows. **Real efficiency win available: pass the flattened entries from `missingBlobHashesInTree` into the caller and skip FlattenTree's redo.** Order-of-magnitude: saves ~one full tree traversal on the hot path. Worth a follow-up. Batch-fetch-all without the missing check would re-download blobs already present from prior recoveries — wasteful in the common re-push case.

**4. `repo.Storer.HasEncodedObject` cost.** Could not read go-git v6 source (sandbox blocked module-cache paths). go-git's filesystem storage loads packfile indexes lazily and probes index fanout — effectively O(log n) per packfile, with index pages mmaped. Not free but not a scan. For thousands of blobs this is microseconds, dwarfed by the network fetch.

**5. `FetchBlobs` ARG_MAX risk.** Confirmed in `cmd/entire/cli/checkpoint/remote/git.go:85`: every hash is appended as a CLI argv to `git fetch-pack`. ARG_MAX on macOS/Linux is ~256KB–2MB.
