# Type Design Review — onboarding ladder (branch `cli-onboard`, `git diff main...HEAD`)

## Package `cmd/entire/cli/onboarding` (onboarding.go)

### Type: State

**Invariants identified**
- Exactly five valid values; `String()` must emit stable machine-readable names consumed by `status --json` (`status.go:670`).
- Zero value is `StateUnknown`.

**Ratings**
- **Encapsulation**: 7/10 — Plain int enum, standard Go. Nothing prevents `State(42)`, but `String()` collapses out-of-range values to `"unknown"` (onboarding.go:52), which is the right fail-safe for a JSON surface.
- **Invariant Expression**: 8/10 — Each constant has a doc comment explaining semantics including examples; the "stable machine-readable name" contract is stated at `String()` (onboarding.go:38).
- **Invariant Usefulness**: 9/10 — The zero value being `StateUnknown` is a genuinely good choice here, and the semantics compose safely: an accidental zero-value `Check` contributes to `total` but never to `done` in `Summary()` (onboarding.go:107-118), so `Complete()` can never be true by omission, and `Missing()` deliberately excludes Unknown (onboarding.go:129) so a broken probe never triggers an offer. Fail-safe in both directions.
- **Invariant Enforcement**: 6/10 — No exhaustiveness protection: adding a sixth state compiles silently and renders as `"unknown"` in JSON and `"?"` in `onboardingRowMarker` (onboarding_render.go:72-82). The default-case fallthroughs mask a missing switch arm rather than surfacing it.

**Recommended improvement**: consider `//exhaustive` lint annotations or a test asserting `String()` round-trips every constant, so a new state can't silently degrade to `"unknown"` in the `--json` contract.

### Type: Check

**Invariants identified (all conventional, none enforced)**
- `Detail` is a short human fragment; `Hint` is an exact runnable command.
- Convention by state: Done → Detail set, no Hint; Missing/Blocked → Hint set (it feeds the "run later" lines at onboarding_offer.go:134-140); Unknown → Hint set but Detail often empty; NotApplicable → Detail only.
- The renderer *knows* this coupling: onboarding_render.go:50 special-cases "Unknown with empty Detail borrows Hint into Detail" because Unknown rungs are excluded from `Missing()` and their hint would otherwise never surface.

**Ratings**
- **Encapsulation**: 4/10 — Three exported fields, all independently settable. Any combination is representable, including nonsense (`StateDone` with a retry Hint, `StateMissing` with no Hint — the latter silently produces a red ✗ row with no recourse and no "run later" line).
- **Invariant Expression**: 5/10 — Field comments are good, but the per-state coupling rules live partly in comments and partly in the renderer (`onboarding_render.go:47-52`). A reader of the type alone cannot learn that "Missing implies Hint" or that Unknown's Hint is rendered through Detail.
- **Invariant Usefulness**: 8/10 — The State/Detail/Hint triple is exactly the right shape for the three consumers (checklist row, run-later line, JSON state). The invariants would prevent real bugs (a missing rung with no follow-up command is a UX dead end).
- **Invariant Enforcement**: 3/10 — Nothing at construction. Every rung constructs `Check{...}` literals by hand (nine sites in onboarding_rungs.go), each re-remembering the convention.

**Recommended improvements**
- Add small constructors in the `onboarding` package: `Done(detail string)`, `Missing(detail, hint string)`, `Blocked(detail, hint string)`, `Unknown(hint string)`, `NotApplicable(detail string)`. This makes "Missing carries a hint" a signature, not a convention, collapses the nine literal sites, and lets `Unknown(hint)` document the Detail-borrowing rendering rule at the source rather than in the renderer. Cheap, non-breaking (keep the struct exported).
- Alternatively (lighter): a `Check.EffectiveDetail() string` method owning the Unknown-borrows-Hint rule, moving that coupling out of `renderOnboardingChecklist` (onboarding_render.go:50) into the type that owns the fields.

---

### Types: Rung, Ladder, Result, Key* constants

**Invariants identified**
- `Rung.Check` must be non-nil (implicit — `Ladder.Checks` at onboarding.go:98 dereferences it, panicking otherwise).
- `Rung.Check` must not prompt (comment-only, onboarding.go:71) and must be safe to run concurrently (comment at onboarding.go:87-90).
- `Rung.Key` should be one of the `Key*` constants and unique within a `Ladder` (implicit — the offer runner's `offerFns` map and `statusJSON.Setup` map both key by it; a duplicate key would silently lose an entry in JSON).
- `Ladder` order is meaningful (offer order, checklist order).

**Ratings**
- **Encapsulation**: 5/10 — Everything exported and mutable, but this is a deliberate "data, not interface" design and the package comment says why (onboarding.go:66-67). For a four-rung ladder built in one factory (`onboardingLadder`, onboarding_rungs.go:80-82), that's proportionate.
- **Invariant Expression**: 7/10 — The struct-with-func-fields choice is well argued and correct for this size: closures capture `onboardingRungDeps` naturally, tests build fake rungs inline (onboarding_test.go does exactly this), and an interface would add four single-method types for zero polymorphism gain. The "must not prompt" and concurrency contracts are stated, though only in prose.
- **Invariant Usefulness**: 8/10 — The Key-as-shared-identifier design is what keeps enable's offers, the checklist, and `status --json` from disagreeing — the package's stated purpose. Order-as-data cleanly encodes offer sequencing (login unblocks mirror in the same pass, onboarding_offer.go:100-124 depends on ladder order).
- **Invariant Enforcement**: 4/10 — Nil `Check` panics in a goroutine inside `Checks()` — the worst place to discover it. `Key` is an untyped string with no tie to the `Key*` constants; a typo'd key silently detaches a rung from its offer (`offerFns[res.Rung.Key] != nil` at onboarding_offer.go:89 just filters it out — no error, the rung becomes permanently un-offerable). Duplicate keys are unchecked.

**On Rung vs interface**: struct-with-func-fields is the right call at this scale. The verdict would flip if rungs grew a third behavior (e.g. per-rung JSON detail) — at that point an interface with a base struct beats a widening bag of func fields.

**Concern — dead field**: `Rung.Offer` (onboarding.go:75) is never assigned or read anywhere in the diff. The offer mechanism that actually shipped is the parallel `offerFns map[string]func` on `onboardingOfferRunner` (onboarding_offer.go:38, wired at onboarding_offer.go:164-168). Two mechanisms exist for one concept; one is dead. Either delete `Rung.Offer`, or move the three offers into it and drop `offerFns` — the map-keyed-by-string indirection is strictly weaker (a key typo is a silent no-op) than a field on the rung itself. The field's own doc comment ("e.g. import until the enable-time offer lands") suggests it's speculative; import's offer nonetheless landed in the *map*, so the speculation already expired.

**Recommended improvements**
- Resolve the `Rung.Offer` / `offerFns` duplication (prefer keeping `Rung.Offer`, since it makes "this rung has an offer" a property of the rung, checked at construction, instead of a string-keyed lookup).
- If both stay data, add a cheap `Ladder` validity check (non-nil Check, unique keys) exercised by a test against `onboardingLadder(...)` — one test, permanent protection.
- Optional: `type Key string` for the constants to prevent arbitrary strings; low cost since all producers/consumers are in-repo.

## Package `cli`

### Type: onboardingRungDeps (onboarding_rungs.go:31-46)

**Invariants**: all eight func fields non-nil; `authed` must be side-effect-free and non-prompting (it wraps `authRung(deps).Check` — onboarding_rungs.go:73-75); `resolveOrigin` returns `"gh"` for GitHub per gitremote semantics; `probeMirror` receives lowercased owner/repo (stated at onboarding_rungs.go:134-135 and honored at the call site, onboarding_rungs.go:285).

**Ratings**: Encapsulation 6/10 (unexported, constructor exists, but zero value panics deep inside a concurrent `Checks()`); Expression 8/10 (every field documented, including the deliberate offline-not-RefreshedLoginToken choice at onboarding_rungs.go:58-59 — excellent); Usefulness 9/10 (this seam is why the rung tests run without keyring/network, exactly as claimed); Enforcement 4/10 (nothing stops a test from injecting a partial deps and hitting a nil-func panic; the lowercase precondition on `probeMirror` is prose-only).

**Suggestion**: the lowercasing precondition is split between the rung (onboarding_rungs.go:277,285) and the probe's doc; safer to lowercase *inside* `probeRepoMirrored` (onboarding_rungs.go:137) so the cache key can never fork on case. One line, removes a cross-function invariant.

### Type: agentImportStatus (onboarding_rungs.go:49-55)

Honest DTO; field comments good. One expression gap: the population site maps `UnimportedTurns: res.TurnsImported` (onboarding_rungs.go:232) — correct only because the run is `DryRun: true`, where "imported" means "would import". That inversion reads like a bug until you check the options five lines up. A one-line comment at onboarding_rungs.go:232 ("dry-run: TurnsImported = would-import") would pay for itself. Also note this type doubles as the import-cache's persisted schema (`importScanEntry.Statuses`) — a rename changes on-disk format; the fingerprint mechanism happens to absorb that, but a comment noting the dual role is warranted. Ratings: 6/8/8/5.

### Types: onboardingOfferRunner + onboardingSetupMode (onboarding_offer.go)

**onboardingOfferRunner** — same seam pattern, same trade-offs as deps: all six fields required, constructor wires production, zero value panics at `r.styles(w)` (onboarding_offer.go:127). Expression is a highlight: the type comment (onboarding_offer.go:29-35) states the key behavioral invariant — recompute state before each offer, so re-running enable is the resume path — and `runOffers` visibly enforces it (re-check at onboarding_offer.go:107). `patchSucceededOffers` (onboarding_offer.go:70) encodes a subtle eventual-consistency invariant with a clear comment. Ratings: 6/9/9/5.

**onboardingSetupMode** — the one enum where the zero value is the *most permissive* option: `setupModeAll = iota` (onboarding_offer.go:20) means a forgotten or defaulted mode runs every offer, including a login and a network mirror-create. Today it's safe — `run()` maps prompt errors to `setupModeSkip` (onboarding_offer.go:55) and `mode := setupModeAll` at onboarding_offer.go:180 is an intentional preselect — but it inverts the fail-safe convention `State` gets right. Reordering so `setupModeSkip = iota` costs one line at the preselect and makes "zero value = do nothing to the user's account" structural. Ratings: 6/7/8/5.

### Types: mirrorProbeCache/mirrorProbeEntry, importScanCache/importScanInput/importScanEntry, availableMirrorLister

**mirrorProbeEntry** (onboarding_mirror_cache.go:41-45) can represent the illegal state `{Mirrored: true, Unreachable: true}`. It's guarded in practice — the only writers are `put` (never sets Unreachable) and `putUnreachable` (never sets Mirrored), and `write` is the sole file-touching path — good procedural encapsulation. But `get`'s `(mirrored, unreachable, ok bool)` triple (onboarding_mirror_cache.go:60) is three-boolean blindness; the call site (onboarding_rungs.go:140-145) must remember unreachable-wins ordering. A tiny sum-shaped result (`type probeResult int: probeMiss, probeMirrored, probeNotMirrored, probeUnreachable`) would make both the entry's illegal state and the caller's branching disappear. Note also the write-through at onboarding_offer_actions.go:109 — a second producer outside the probe path; it honors the invariant but is the kind of thing the sum type would keep honest. Ratings: 7/7/9/6.

**The two caches sharing structure**: the load/marshal/mkdir/write plumbing is duplicated nearly verbatim (onboarding_mirror_cache.go:51-58,83-95 vs onboarding_import_cache.go:63-70,80-92 — including the identical nolint comment). The *invalidation policies* are genuinely different and should stay separate types: TTL-with-failure-window vs exact fingerprint is the essential design content of each. But the persistence shell is incidental and is exactly the ~10-line duplication this repo's `mise run dup` (threshold 50) exists to catch. A small generic `jsonFileCache[E any]` with `load() map[string]E` / `store(key string, e E)` in one place would keep both policy types thin without merging their semantics. I'd stop short of unifying `get` semantics — forcing TTL and fingerprint through one interface would be over-abstraction. Import cache ratings: 7/8/9/6 (the order-independent fingerprint with the `cacheable` poison flag for vanished files and partial results, onboarding_rungs.go:183-236, is careful, well-commented invariant work — the best enforcement in the PR).

**availableMirrorLister** (onboarding_rungs.go:86-89) — textbook consumer-side interface: two methods, defined where consumed, named for what it does, with `CoreOrigin()` doing double duty as the dedupe key in `probeMirrorAcross` (onboarding_rungs.go:102). Nothing to change. Ratings: 9/9/9/8.
